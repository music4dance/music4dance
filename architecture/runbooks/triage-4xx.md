# Triage Production 4xx Errors

**Type:** Runbook
**Status:** Current
**Last verified:** 2026-10-01

## When to use

Periodically (every few weeks), or whenever the "HTTP 4xx Errors" table on `/Admin/Diagnostics`
shows new top URLs. The aim is to separate scanner noise from real music4dance bugs, widen the
known-attack filter where that's safe, and keep a record so recurring noise isn't re-investigated.
How the tracker works is described in
[bot-and-abuse-defense § Layer 4](../security/bot-and-abuse-defense.md#layer-4-4xx-by-url-tracking-http4xxtracker).

## Prerequisites / access

- An admin account on production.
- Ideally the `analyze-4xx` Claude Code skill (`.claude/skills/analyze-4xx/SKILL.md`), which
  automates the steps below and appends to the triage log.

## Steps

1. Export: `GET /Admin/Http4xxExportCsv` downloads every distinct URL, **excluding** the known
   attacks. Save it as `local/4xx-urls-YYYY-MM-DD.csv`.
2. Check each high-volume pattern against the **triage log** below *first*. Investigate only
   what isn't already covered.
3. Classify each new pattern as one of: bad actor / scanner, benign platform probe, external
   (stale or mangled link), known bot pattern, or **internal bug**.
4. For scanner patterns that name a file or route this app has never served and never will, add
   them to `Http4xxTracker.KnownAttackPathPrefixes` / `KnownAttackPathSubstrings`, and add test
   cases to `Http4xxTrackerTests.IsKnownAttackUrl_ClassifiesKnownPatterns` in **both**
   directions. Keep short generic segments a future feature might use (`/login`, `/mcp`,
   `/dashboard`) and benign probes (`/sitemap.xml`, `/.well-known/*`, `/apple-touch-icon*`)
   *out* of the list, so they stay visible.
5. Fix internal bugs in their own PRs.
6. Add a row to the triage log for **every** pattern triaged in this pass, including ones
   deliberately left alone.

## Verification

After deploy, the "Excluding known attacks" view of `/Admin/Diagnostics` should no longer show
the newly classified scanner patterns, and the fixed internal URLs should stop accruing hits.

## Rollback

Known-attack patterns only affect classification and filtering, never request handling, so a
bad pattern is fixed by removing it in a follow-up PR.
